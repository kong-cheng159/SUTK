# 经验总结 —— 《三国志·汉末篇》存档修改实战复盘

> 这份文档记录 2026-10-25 一整天踩的坑与提炼出的方法论。
> 核心结论只有一句：**任何"原版存档里从不出现的状态"，就是非法状态。**

---

## 一、这次到底发生了什么

一整天翻了 4 次车，最后才让一个存档稳定可读。把时间线摊开看，教训很清楚：

| 时间 | 现象 | 我当时的判断 | 真实原因 |
|---|---|---|---|
| 18:30 | 全吞并后游戏卡死 | "游戏不支持 0 城势力" | **误判**（真凶是太守任职时间没清零） |
| 19:05 | 读档后走时间崩（`0x4568`） | 猜了一堆字段 | 太守 `staffId` 清了但 `staffAccTime` 没清零 |
| 19:25 | 又崩 | 猜"AI 打自己城" | 城市易手后 AI 目标没更新 |

**五次失败里，有四次是我用"猜"代替了"取证"。**

## 二、核心方法论：原版基线法

### 原则

不要问"这个值看起来合不合理"，要问"**游戏自己的存档里有没有出现过这种状态**"。

游戏原版存档就是**基线**。把 `backup\` 下所有 `.orig`（游戏原封不动写出的存档）扫一遍，
统计每个字段的取值分布。凡是**只在你的存档里出现**的组合，就是你造出来的非法状态。

### 实操四步

```python
# 1. 拿到原版基线：所有游戏原档
for n in os.listdir(BACKUP_DIR):
    if n.endswith('.orig'):
        base[n] = json.loads(read_sav(...)['body'])

# 2. 找出你的存档和基线的差异字段
diff = flatten(my_save) vs flatten(base)

# 3. 把差异字段拿去扫全部基线：只在我档里出现的 = 非法
for field in diff_fields:
    if (field, value) not in baseline_values:
        print('非法状态:', field, value)

# 4. 修掉它，再验一遍
```

### 三次成功的应用

**① 太守任职时间**

```
原版：prefecturalUnit.staffId = 'None'  ->  staffAccTime 恒为 0
我改：prefecturalUnit.staffId = 'None'  ->  staffAccTime = 305   ← 非法
```

游戏看到 `staffAccTime=305` 就认为"这城有太守、已任职 305"，去取太守对象 → **null**。
崩溃地址 `0x4568` = 空指针 + 成员偏移，正好对上。

**② 城市易手后 AI 目标没更新**

游戏让城易手时，会把 `architectureAI.readyAttackTargetArchitecture` 一起改掉。
我没改 → 城在"攻击自己" → 寻路找不到目标 → 同样的 `0x4568`。

**③ 武将住在敌城**

```
原版：住在非本势力城里的武将 = 6~45 人（游戏自然产生的，很常见）
我改：78 座城换主 → 变成 239 人（4 倍）
```

游戏读档后第一帧要把这些人搬回本势力首都，**这条搬迁路径本身有 bug**，
搬的过程中就崩。修法不是修游戏，而是**提前搬好**：

```python
personages[pid]['info']['architecture'] = 本势力首都
```

## 三、崩溃取证流程（以后照这个做，别猜）

游戏是 UE5，崩溃会留下完整现场：

```
%LOCALAPPDATA%\ProjectA\Saved\Crashes\UECC-Windows-<hash>_0000\
├── CrashContext.runtime-xml    ← ErrorMessage / SecondsSinceStart
├── ProjectA.log                ← 崩溃前的完整日志（最有价值）
└── UEMinidump.dmp
```

### 关键三步

**① 看崩在哪个阶段**

| 现象 | 结论 |
|---|---|
| 日志里已有 `Panel Open : GameMainPanel`，之后才崩 | 读档成功，崩在**运行中** |
| 崩在读档阶段、帧号很小（<300） | 崩在**加载后第一帧** |
| `SecondsSinceStart` 很大（几百秒） | 玩了一会儿才崩 → 定时结算路径 |

**② 看崩溃前最后几行日志**

```bash
# 崩溃日志里倒数 20 行，忽略 "elapsed time" 噪声
```

这一步直接点名凶手。20:24 那次，最后三行是：

```
City:YangPingGuan Remove Personage:ZhangJin
Personage:ZhangJin, Transfer City-- From:YangPingGuan To HanZhong
City:HanZhong Add Personage:ZhangJin   ← 崩在这
```

**一眼就知道**：游戏在搬武将，搬崩了。

**③ 用帧号和"是否加载成功"分流**

不要一上来就怀疑存档坏了。先确认：
- 存档能读进内存吗？（`read_sav` 能解析）
- 游戏能加载吗？（日志有 `Panel Open : GameMainPanel`）
- 崩在第几帧？

## 四、存档格式的硬性规则

### 1. 文件命名（不改名 = 存档列表里看不见）

```
<君主中文名>-<年号>(<年>)<月中文><日中文><时支>.sav

例：郑成功-中平二年(185)二月十五丑时.sav
    郑成功-中平三年(186)六月初一子时.sav
```

- 年号 = 年份 - 183（184 = 中平元年）
- 月：正月 / 二月 … / 十月 / 十一月 / 腊月
- 日：初一…初十 / 十一…十九 / 二十 / 廿一…廿九 / 三十
- 时支：子丑寅卯辰巳午未申酉戌亥，由 `gameTime.dayTickCount` 决定

### 2. 存档结构

```
magic   'BO-QI-DAO-ProjectA-ZLIB-1'
header  JSON: sceneId/version/saveTime/gameTime/gameSetting/kingId/…
body    JSON: factions / architectures / personages / empire / factionRelations / …
```

`header` 和 `body` 是分开存的，改 body 时保留 header 即可。

### 3. 成对字段（改一个必须改另一个）

| A | B | 不成对的后果 |
|---|---|---|
| `prefecturalUnit.staffId` | `prefecturalUnit.staffAccTime` | 空指针崩（`0x4568`） |
| `areaUnitList[].staffId` | `areaUnitList[].staffAccTime` | 同上 |
| `architectures[].info.faction` | `personages[].info.architecture` | 读档搬迁崩溃 |
| `architectures[].info.faction` | `factions[].info.capitalId` | 0 城势力 → AI 卡死 |
| `architectures[].info.faction` | `architectureAI.readyAttackTargetArchitecture` | AI 打自己城 → 崩 |
| `factions[].info.faction` | `empire.info.emperorId` | 皇帝势力被灭 → 读档崩 |

### 4. 大小写陷阱

城市 key 是驼峰（`nanHai`），但 `capitalId` 里是大驼峰（`NanHai`），
武将 `prefectId` 是大驼峰（`YuanShu`）而 `personages` 的键是小驼峰（`yuanShu`）。
**所有按名字查表的字典，键必须统一 `.lower()`。** 我为这个错栽了两次。

**第三次栽（外交/好感度全部失灵）**：自建武将开新势力后，`factions` 的键是
`new_6`（小写 n），但外交关系表 `factionRelations` 里的 ID 写的是 `New_6`
（大写 N）。精确匹配一条都对不上 → 控制台外交表空白不显示国家、
好感/同盟/停战写入全部跳过（提示"已写入 0 条"）。教训：
**每新增一个"按势力 ID 查表"的功能，都必须过一遍 `.lower()` 归一**，
城市模块当年就是这么修的，外交模块漏了。

## 五、势力操作的三条铁律

### 铁律一：不要随意"灭亡"势力

实测把 29 个势力标成 `bDestroyed=True` 会连带崩掉，因为：

- `empire.info.seigneurIds` / `independentIds` / `empireFactionDatas` 仍按 id 引用它们
- `empire.info.emperorId = "29"`（汉献帝一系）——把皇帝灭了必崩
- `factionRelations` 是 34 个势力的两两关系矩阵（561 条），引用无法简单清理

**正确做法**（本次采用的）：**一个势力都不灭**，每个小势力保留自己的首都一座，
其余城池按地域分给三大。这样结构与原版完全同构，读档零风险。

### 铁律二：城池易手后要连带处理的字段

```
info.faction              改归属
info.prefectId            清空
prefecturalUnit.staffId   清空 + staffAccTime 归零
areaUnitList[].staffId    清空 + staffAccTime 归零
lastFactionName           记原主（游戏自己会写这个）
architectureAI            清掉"打自己城"的目标
guardTroopKindId          守军兵种要跟着新主
```

### 铁律三：武将要跟着家走

改了城归属后，把武将的 `info.architecture` 改回本势力首都，
否则游戏读档时自己去搬人，那条路径有 bug。

## 六、工具侧的经验

### 1. 历史快照（history）

改档前自动把"改之前的样子"存一份到 `SUTKMod\history\`：

| 触发 | 备注 |
|---|---|
| 写档前 | `auto` |
| 应用修改前 | `apply` |
| 转移城市前 | `pre_transfer` |
| 回滚前 | `before_restore` |
| 游戏自己存档 | `game`（默认关，避免堆积） |

- 按 **sha1 去重**：内容没变不重复存
- 每存档留 30 份，超了删最老的
- 回滚两段式：**先选存档 → 再选版本**（1 = 最近，末项 = 原始档）

### 2. 自动清理的教训

游戏重写 `AutoSave.sav` 时文件会**消失几十秒**。我最初按"6 秒没看到就算删档"，
结果把原始备份 `.orig` 误清了。

修正：
- 判定改成 **30 秒**（`REAP_STRIKES = 15`）
- **自动清理只清历史快照，`.orig` 永远留给手动 `M → 8`**
- 清走 `.orig` 前，先把武将名录并入 `_roster_merged.txt`（否则"自建武将识别"会退化）

### 3. 写文件的坑

- **bat 必须 GBK + CRLF**（`chcp 936` 后 cmd 按字节重读，UTF-8/LF 会把行截断）
- **文本模式写 `\r\n` 会变成 `\r\r\n`** → 必须 `open(..., 'wb')` 或 `newline=''`
- **改完同步到安装目录** `%LOCALAPPDATA%\SUTKMod\`，否则跑的还是旧版

## 七、现在的检查清单

改完存档，**必跑**：

```
控制台 → V（存档审计）
```

它会检查：

**硬性问题（必崩）**
- 存活势力有城、首都有效且属于自己
- 皇帝势力健在（有城、有首都）
- `staffId` 与 `staffAccTime` 成对
- 岗位武将存在
- 武将居住城存在
- 城市 AI 不打自己的城
- 势力级城市引用不指向不存在的城
- 部队将领存在
- 帝国/外交里不挂着已灭亡势力

**基线对比（与原版比，超出才算问题）**
- 武将住在敌城的数量 vs 原版平均
- 岗位武将归属错配数量 vs 原版平均
- 优先粮食城指向别国的数量 vs 原版平均

> 注意：审计本身也踩过坑——第一版把"武将住敌城""计略指向别国"当硬性错误，
> 结果**原版存档自己就报错**。说明任何检查项都必须先过原版基线这一关。

## 八、附：自己造剧本的做法

以「三分天下」为例（`三分天下.py` / `_three_way_soft.py`）：

1. 写一张**城市 → 地域**对照表（122 座城全覆盖，不许漏）
2. 每家小势力**保留自己的首都**，其余城池按地域分给三大
3. 玩家保留指定城池（南海），实力原样不动
4. **不动**：`bDestroyed` / `empire` / `factionRelations` / 武将归属 / 部队归属
5. 连带处理：太守、驻守、任职时间、守军兵种、AI 目标
6. 提前把武将搬回自家首都
7. 改完跑 `--audit`，必须全过
8. **另存为新档**（不覆盖原档），文件名按规范生成
9. 玩家读档前，先把游戏退到主菜单（游戏还在跑会覆盖）

## 九、外交字段：关系 ≠ 人情

游戏外交界面上的两个数字，在存档里是两套完全不同的东西，改错一个等于没改：

| 界面名 | 存档字段 | 含义 | 范围 |
|---|---|---|---|
| 关系 | `factionRelations[].relationValue` | 两国关系，影响 AI 态度/结盟意愿 | -100 ~ 100 |
| 人情(我) | 同条目 `favourValue1/2`（玩家那一侧） | 帮过对方攒下的人情，请求支援时消耗 | 0 ~ 约 20 |
| 人情(他) | 同条目另一侧的 `favourValue1/2` | 对方持有的人情（AI 可用来向你提要求） | 0 ~ 约 20 |

- 后缀 1/2 分属 `factionId1` / `factionId2` 两侧（和 `diplomatist1Id`、`intelEvent1` 同一命名规律）
- 人情来源：`DONATE_MONEY_FAVOUR` / `DONATE_CONSCRIPTION_FAVOUR`（捐钱/捐兵）——**出力方**获得人情；
  请求支援时消耗（exe 里「人情值:%f」和 `RequestSupport失败` 是相邻的日志串）
- 人情有上限和衰减：exe 里 `FAVOUR_MAX`、`FAVOUR_ATTENUATION_CD`、`FAVOUR_ATTENUATION_VALUE`；
  存档里 `favourChangeTick1/2` 记录上次变化时间。**写人情时必须同步把 tick 重置为当前 tick**，
  否则可能立刻被判定为过期而衰减
- `improveValue` 是"改善关系"动作的进行量（日志里「停战：%d, 同盟：%d，改善关系：%d」），由游戏自己维护，别碰
- 判断字段方向的办法：找**同时有两个合法值**的条目（如 fv1=18.9 / fv2=20），配合 exe 符号的语义命名，
  再决定写哪一侧；不确定就两边都做成可调，让用户在游戏里验证

## 十、一句话总结

> **别猜，去取证。**
> 游戏会把它认为"不可能发生"的状态直接写成崩溃。
> 找到那份原版存档，比任何推理都可靠。
